## Regra de contingência — GitHub Free nunca paralisa a operação (ordem do Mestre)

**PRIORIDADE OPERACIONAL:** a cota do GitHub Free para repositórios privados é **2.000 minutos de Actions por ciclo**, compartilhada na conta do proprietário. O GitHub é OPCIONAL e TRANSVERSAL; Comestres podem trabalhar nativamente no ChatGPT quando GitHub estiver indisponível, caro em minutos, inacessível ou sem franquia. A conta real e seu saldo não foram auditados; não inventar minutos restantes. Sem upgrades pagos, nem tornar código privado público.

**Antes de depender da CI:** avaliar se GitHub ajuda realmente a mudança; escolher suíte mínima adequada. Verificar, quando o acesso ao painel permitir, saldo GitHub Actions. Falta de resultado pode ser quota, billing, fila, erro do runner, autorização ou de código: identificar a causa antes de tratar como regressão.

**Protocolo de fallback executável na mesma conversa (sem nova operação):**

1. Marcar `GH-QUOTA` / `GH-BILLING` / `GH-ACCESS` / `GH-RUNNER` / `GH-OUTAGE` / `GH-QUEUE` / `GH-SKIPPED-TO-SAVE-QUOTA` quando for problema externo, distinto de `CODE-FAIL`.
2. **Seguir trabalhando na operação legítima**, executando nativamente no ChatGPT a **fonte original de código e testes** (arquivo e versão/hash conferidos, cópia TEST isolada, execução por Python/container ou ferramentas computacionais realmente disponíveis), analisando falhas e corrigindo o código TEST. Não criar motor alternativo ou simular logs.
3. Emitir recibo objetivo `LOCAL-TEST-PASS|FAIL|NOT-RUN`, nome do motor, fonte/hash, data, scripts, seed quando pertinente, número de testes executados, falhas, limitações, link ao artefato quando houver e status `GH-NOT-RUN`. A ferramenta não deve afirmar execução/certificação no GitHub nem prometer retorno futuro.
4. Se faltar origem, ZIP ou runtime no ChatGPT, registrar `TEST-BLOCKED-MISSING-SOURCE/RUNTIME` e avançar em tarefas independentes. Falta de testes locais não pode virar PASS; nenhuma nova obrigação de instalar ferramentas, pagamento ou PC.
5. Se GitHub PR estiver em FAIL ou PENDING **por ausência de CI**, manter `CI-HOLD` para merge no GitHub até cumprir os gates daquela PR; o Comestre continua depurando e produzindo evidências locais. O bloqueio de merge TEST remoto não é STOP universal do VLAB/CRAFT/LEVEL-UP/DMG e muito menos promoção canônica.
6. Recuperado o GitHub, usar novamente só quando houver benefício real ou gate de CI obrigatório. Não repetir o corpus antigo inutilmente. Manter Party, O Primeiro, fichas oficiais, cânone e laboratórios alheios sem escrita.

**Estado global exigido:** `GITHUB-HOLD / OPERATION-CONTINUES-NATIVE` em contingência. **Nenhuma operação depende exclusivamente de GitHub**. A cota pode ser economizada na CI com filtros de caminhos e cancelamento de runs obsoletos, desde que os testes exigidos de código ainda rodem.

## FLUXO PRÁTICO PRIORITÁRIO — GitHub responde no mesmo atendimento

**Decisão vigente do Mestre:** sincronização Notion→GitHub automática não é requisito. Ao concluir uma alteração de programação no Notion, o Comestre pode usar o GitHub na MESMA CONVERSA para publicar uma **cópia TEST da mudança real** (não só reexecutar um ZIP antigo), verificar a resposta e corrigir sem abrir outra operação.

1. **ANTES:** ler este AGENTS.md, a diretriz GH-RP-01, a última entrada do Diário e os arquivos reais. Confirmar conexão GitHub, operação responsável, origem/versionamento/hashes e permissão TEST. Se não houver código que corresponda à nova mudança, não fingir que o GitHub testou a versão do Notion.
2. **ENVIAR:** criar branch TEST a partir de `main`; atualizar `proposals/vlab/candidate.json` ou `proposals/levelup/candidate.json` nos módulos aceitos pelo runner (ou adicionar suporte específico com revisão); abrir PR. A PR, não uma mensagem livre de chat ao GitHub, dispara o GitHub Actions. O código original permanece intacto e a alteração da proposta roda apenas em cópia temporária.
3. **RECEBER NA MESMA INTERAÇÃO, se a execução concluir:** consultar os runs GitHub Actions da PR/commit; verificar conclusão de TODOS os jobs/etapas necessários por API ou conector (status `completed` e conclusion `success`). Se `queued`/`in_progress`, consultar novamente dentro dos limites razoáveis da sessão. O GitHub **não envia respostas espontâneas a esta conversa**; é o Comestre que consulta os resultados com as ferramentas. **Não inventar resposta** e não chamar "verde" um job ainda em andamento.
4. **RED:** ler logs do passo que falhou, registrar erro e corrigir **na mesma PR**, nova execução e nova conferência. Não mesclar RED nem usar um teste irrelevante como prova de PASS. Se ficar bloqueado, deixar PR aberta em HOLD, com resultado verificável e sem prometer monitoramento em segundo plano.
5. **GREEN:** conferir o commit de cabeça exato da PR, o diff e todos os testes exigidos; não confundir sucesso do teste com aprovação de cânone. Para incorporar ao **repositório TEST** utilizar revisão humana/autoridade pertinente e checagem do `expected_head_sha` quando disponível. Depois confirmar o estado da `main`, status dos testes e registrar apenas o marco material no Diário existente. Alterar produção/fichas/Party/O Primeiro continua proibido.
6. **REGRAS DE SEGURANÇA:** não escrever código experimental diretamente em `main`; não fazer force push; não criar novo COMESTRE-ID/Inbox/diário, nem pagar recursos. Como a proteção técnica obrigatória da branch privada **não pôde ser confirmada na configuração gratuita**, esta é uma norma de atuação dos agentes, não uma garantia tecnológica de bloqueio de merge. Nunca declarar enforcement que não foi comprovado.
7. **MÓDULOS NOVOS:** cadastrar fonte, SHA e testes originais apenas quando um Comestre tiver mudança concreta fora dos dois módulos do piloto; preservar scripts legados e os status HOLD.

**Resposta objetiva ao Mestre na mesma mensagem sempre que houver dados concluídos:** `operação | versão TEST | PR e commit | PASS/FAIL/PENDING | testes | causa | correção aplicada | link da execução | resultado após correção | pendências`. Evitar repetição de notas. Se outro Comestre não tiver a conexão GitHub disponível, informar limitação sem inventar acesso.
